# Unknown credential stores are preserved, not rejected

Human authorized autonomous local owner correction; root approved the narrow typed-outcome design and owns publication/adoption. Clean declared worktree, new local fix/preserve-generic-credentials from canonical 432496c6494682b09cad2fc0cb820710e6e8581c. The separate old owner, shared consumer environment, credentials, plugin caches and global configuration were not changed.

The former refresh_credential treated OAUTH_USER as permission to reject and fill. That username proves neither provider identity nor a retained refresh token. Official GCM v2.9.1 and v3.0.2 GitHub/generic erase implementations directly remove stored credentials. GitLab's erase also removes its refresh token. In contrast, GitLab GetCredentialAsync recognizes account oauth2, checks expiry and refreshes through its own retained token without the caller first rejecting it. Primary sources:
- https://github.com/git-ecosystem/git-credential-manager/blob/v2.9.1/src/shared/GitLab/GitLabHostProvider.cs
- https://github.com/git-ecosystem/git-credential-manager/blob/v3.0.2/src/GitLab/GitLabHostProvider.cs
- https://github.com/git-ecosystem/git-credential-manager/blob/v3.0.2/src/GitHub/GitHubHostProvider.cs
- https://github.com/git-ecosystem/git-credential-manager/blob/v3.0.2/src/Core/GenericHostProvider.cs

Automatic reject and its private runtime import are removed. Only an explicit gitlab provider plus oauth2 account and one recognized GCM helper declaration may perform a noninteractive provider-native fill. Generic, unknown, GitHub/Azure assumptions, opaque/custom commands, multiple active helpers, scoped-helper ambiguity and metadata failures KEEP the refused pair with zero additional credential verbs. Empty helper entries reset the chain as Git specifies. GCM_PROVIDER overrides URL-matched provider configuration; no hostname guesses are used. Matching a declared absolute GCM executable basename is not binary attestation: uncertain configurations remain unsupported, and no configured helper command is executed by metadata inspection. This is a narrow documented capability, not a universal OAuth claim.

Metadata uses the public launch door and catches only its applicable OSError/TimeoutExpired failures, preserving the original refusal instead of replacing it with an inspection error. Metadata and native fill receive the same effective environment snapshot/cwd; fill pins the verified oauth2 account. The typed CredentialRefresh carries the actual kept/refreshed state, whether lookup was attempted and a fixed nonsecret reason; its credential field is repr=False. Missing, failed or unchanged provider results retain the original pair. Client uses that state, not a username, and never claims that an unrequested erase happened. Further credential changes require explicit user authorization. No compatibility tuple path or REFRESHABLE_USER alias remains. All real callers and fixtures moved together; the fictitious erase-to-refresh fake store was removed.

The current forge guide corrects its former inference that a first 401 followed by success proves token expiry. This correction prevents future loss; it neither establishes the original 401 cause nor restores an already empty store. No real credential get/fill/reject/erase/login, portable authentication, account recovery or push occurred. Credential operations during tests are function mocks or an isolated temporary fake Git store, never the user's helper/store.
