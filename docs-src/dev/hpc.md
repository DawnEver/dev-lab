# HPC: grants, shared accounts and remote verdicts

- **Two files, two owners.** The JOB file (`-c hpc.toml`, travels with the project) says WHAT runs: `[job]` entry/items/setup/workdir, `[cost]` of one item, `[policy]` for cutting. The MACHINE file says WHERE this box may run: the `[hpc]` table of `~/.config/lab-commons/config.toml` (`lab_commons.config`; `$LAB_COMMONS_CONFIG` overrides the path), holding one `[[hpc.grant]]` per share it holds; the workstation name is `$HARNESS_MACHINE` when the machine harness sets it, else absent (the retired `[hpc] workstation` key is refused by name). Partitions and QOS are cluster facts, so they live on the grant, not the job. A leftover `~/.config/lab-commons/hpc.toml` is refused by name: move it under `[hpc]`.

```toml
[hpc]

[[hpc.grant]]
user = "me"                          # ssh user; keys stay in ~/.ssh/config
hosts = ["login2.cluster", "login1.cluster"]   # login hosts of ONE cluster, tried in order
slurm_account = "acct-free"
cpus = 64                            # this box's share of the account's CPU quota
priority = 0                         # optional tie-break
partitions = ["shortq", "defq"]      # optional, in preference order
qos = { devq = "dev" }               # optional
```

- **An account is `(user, slurm_account)`; its hosts are doors.** Quota and the `lc:ws=` usage tags are per account. The runner tries each host with `ssh -o BatchMode=yes -o ConnectTimeout=10`; exit 255 (unreachable, the command never ran) fails over to the next host and logs it, and the first host that answers stays chosen. A command that ran and failed is NOT a failover. All hosts share Slurm and home, so `status`/`gather`/`retry` read back through any of them (`<job>.run.json` records the targets).
- **Many-to-many, refused by name.** A box may hold several grants; an account may be shared by several boxes, each with its own share. No `[hpc]` table, a duplicate account, an empty `hosts` or a non-positive share is refused with the file and the key named. No secrets in the file.
- **Usage is READ, never stored.** Every job carries `--comment=lc:ws=<workstation>`. The one-round-trip probe also runs `squeue -h --me -A <acct> -o "%C %k"` and sums CPUs per tag (an untagged job counts as someone else's). `--me` matters: a university free-tier account carries thousands of other people's jobs that count against nothing of ours.
- **Allocation is pure** (`plan.allocate`). Per grant: `headroom = min(share, quota - CPUs held by OTHER workstations) - CPUs held by this one`; plan on that headroom with the existing planner; take the grant whose plan finishes earliest (tie: higher `priority`, then file order). No headroom anywhere raises naming every account and why. `probe` prints, per grant, the shares known here against the quota and what each tag holds.
- **Verbs.** `python -m lab_commons.hpc {probe,plan,submit,status,gather,retry} -c job.toml`; `submit` records the grant it chose in `<job>.run.json`, so `status`/`gather`/`retry` go back to the same cluster.

## Remote verdict

Two short calls, NOTHING RESIDENT on the workstation (user ruling 2026-10-09):

1. `python -m lab_commons.hpc verdict submit --sha <40-hex> --repo-url <https> --install "<cmd>" [--needs cargo,cc] [--only ids.txt] [--collect "<pytest paths>"] [--select "<marker expr>"] [--python 3.13] [--repo <local repo>] [-c job.toml] [--history previous-record.json]` -- checks the login node's prerequisites, fetches, builds, collects, plans and submits round 0, writes the run's state ON THE CLUSTER at `~/ci/runs/<sha>/state.json`, prints the run id (the sha) and returns in minutes.
2. `python -m lab_commons.hpc verdict gather --sha <40-hex> [-c job.toml] -o record.json` -- ONE short call: still running (or no login host answered) prints `pending` and exits 3; a finished round is folded and, if a killed shard left ids unfinished, they are re-submitted as the next round (pending again) -- RETRIES ARE DRIVEN BY GATHER CALLS; once nothing is left the record is written to `-o` (the only local write). Then `python -m lab_commons.dev.platformparts record-linux record.json --tier <tier>`.

- **The workstation is untouched** (`tests/test_arch_hpc_leaves_the_workstation_untouched.py`): `lab_commons.hpc` imports nothing of `lab_commons.dev` (no box lock, no environment seat), runs no pytest or interpreter locally, and its only local subprocesses are READ-ONLY git (`show`, `for-each-ref`, `pack-objects`, `rev-parse`, `ls-remote`). A commit off the remote ships as `git pack-objects --revs --stdout` (`<sha>` minus every remote-tracking ref) -- the `git bundle` this replaced needed a temporary ref written into the caller's checkout. The cluster `index-pack`s it into its cache and names `refs/lab-ci/<sha>` THERE.
- **Preparation is reused by its real inputs, never by commit** (`lab_commons.hpc.builds`). The repo declares them once in its pyproject: `[tool.lab_commons.hpc] dependency_inputs = ["pyproject.toml", "uv.lock"]`, `source_roots = ["src"]`, `native = { inputs = ["rust"], build = "<shell writing importable modules into $LAB_CI_NATIVE>" }`. The venv lives in `~/ci/envs/<key>` (key: the inputs' git object ids at the commit + `--install` + `--python`), the native build in `~/ci/native/<key>`, each built once under a `flock`; a sha is only a `git worktree` whose source roots reach them through `PYTHONPATH` (`.lab-ci/env.sh` in the tree, sourced by collection and every array task). A fresh sha with unchanged inputs builds nothing. A git dependency that FLOATS (`name @ git+<url>[@<ref>]`, or a `[tool.uv.sources]` `git` table without `rev`) adds its remote tip (`git ls-remote`, read-only) to the env key, so a new upstream tip rebuilds and an unchanged one reuses -- the pyproject is the one list; a 40-hex pin is already hashed with it. Every env build shares `UV_CACHE_DIR=~/ci/uv-cache`, every native build `CARGO_TARGET_DIR=~/ci/cargo-target` under a `flock`, so a Rust edit compiles only the crates it touched. Each prep step (`env`, `native`, `collect`) prints `@@@ time <step>=<s>s`, appends it to `.lab-ci/prep.log` in the tree, and the record carries them as `prep`. Undeclared, the tree builds its own `.venv` as before.
- **Collection is cached per test file** (`lab_commons.hpc.collect`, shipped as `~/ci/bin/lab_ci_collect.py`): a file's ids are kept under `~/ci/collect/<global key>/<blob id>.json`, the global key hashing the build keys, the marker expression, `pyproject.toml` and every `conftest.py`; only files with no entry are collected, in one pytest call, and a file that failed to collect is never cached. Used when `--collect` is paths only (test files = tracked `test_*.py`/`*_test.py`); an option in it falls back to one plain `pytest --collect-only`.
- **`--only <ids-file>`** (one node id per line) runs just the ids the caller selected -- the selection is the repo's.
- **Prerequisites are named up front**: `git`, `uv` and every `--needs` command must be on the login node's `PATH`, else submit refuses naming them before anything is fetched. **A failed build stops the verdict**: the install runs in its own `bash -eo pipefail`, its output is kept at `~/ci/trees/<sha>/.lab-ci/build.log`, and a non-zero exit (or no `.venv/bin/python` after it) refuses with the log's tail -- measured 2026-10-09: a build that failed for want of `cargo` went on to submit 276 shards that all died on `.venv/bin/activate`.

- Everything on the cluster lives under `~/ci/`: `cache.git` (bare, fetched read-only over HTTPS), `packs/<sha>.pack` (only when the commit is not on the remote: a read-only pack from `--repo`, base64 over the runner's stdin), `runs/<sha>/state.json` (the run between gathers), `trees/<sha>` (a worktree with its OWN `.venv`, built once on the login node and reused), `bin/lab_ci_pytest_item.py` (the item runner, shipped from this checkout so its parser does not depend on the tested project's `lab_commons` pin). A day-to-day `~/<repo>` checkout is never touched.
- Node ids come from `pytest --collect-only -q` in the tree (`--select` and the platform expression join into ONE `-m`, since pytest keeps only the last); one item per test file. Each item runs `pytest <its files> -p no:cacheprovider -p lab_ci_pytest_item -q [-n 0]` and the plugin keeps only its ids (`LAB_CI_IDS`) -- ids never go on the command line, because pytest cannot parse back every id it prints (a `::` or an escaped non-ASCII character inside a parameter) and one it cannot parse aborts the file with `no tests ran` -- the runner is also the pytest PLUGIN, and `-n 0` (when xdist is installed) keeps an item on its one CPU instead of starting a worker interpreter per file.
- **Outcomes are STREAMED, keyed by pytest's own `nodeid`.** The plugin appends one JSON line per test phase to `.lab-ci/<stamp>-r<round>/<item>.jsonl` as pytest reports it; the runner closes the file with `{"done": rc, "wall": s, "peak_mb": m}`. The verdict reads the streams (one `cat` per round), not the shards' end-of-run files. An xdist `@<group>` suffix is stripped back to the collected id. Measured on a real cluster (a downstream verdict, 2026-10-09): the junit file this replaced keyed on `(classname, name)`, `--dist loadgroup` had renamed grouped tests `<name>@group_0`, and 8786 tests that RAN were recorded `missing`.
- **A kill costs only the unfinished.** An item whose stream never closed (a shard Slurm killed for `TIMEOUT`/`OUT_OF_MEMORY`) keeps what it reported; its remaining ids are re-submitted split in halves, for up to `verdict.RETRIES` (2) more rounds, the next round asking for twice the memory after an `OUT_OF_MEMORY`. Only what is still unfinished after that is `lost`. Same run: 23 of 99 shards hit the 2h09 limit and 3 were OOM-killed at 6 GB, and the old atomic results file made all 13751 of their ids `lost`.
- **The plan is measured.** The record carries `durations` (seconds per id), `overheads` (per file: wall minus its tests -- interpreter and imports) and `peaks_mb` (per file). `--history <previous record>` feeds them back: an item costs its file's overhead plus its ids' durations, shards are packed consecutively by that time inside the `[policy]` window, the wall limit is the slowest shard's sum times `policy.safety`, and the memory is the worst measured peak times `policy.safety`. `[cost]` prices only files never measured, and each round's plan names them as `unmeasured`. Same run: a flat `seconds = 120` per file planned 129-min shards that ran 1h25-2h07.
- **Compute-node set-up is the grant's.** `setup = ["module load ..."]` in `[[hpc.grant]]` is prepended to every array task that grant submits, before the job's own set-up (e.g. `module load git/2.42.0` -- its compute nodes have no `git`, and 126 git-calling tests errored `FileNotFoundError: 'git'` on the same run).
- The record `{sha, platform, cluster, python, prep, plan, rounds, outcomes, handed, durations, overheads, peaks_mb}` is written to `-o` (`plan` is round 0's). Outcomes: `passed`, `failed`, `error`, `skipped`, `xfailed`, `not-covered` (assigned to another part, by the platform table and rule below), `lost` (unfinished after every retry), `missing` (its item's pytest closed without reporting it -- a crash mid-file, or an id the collection no longer yields). Only `passed` means passed. `handed` maps each `not-covered` id to the platforms that CAN run it (`[]`: none).
- The tested tree's venv must provide `lab_commons.hpc.worker` (any `lab-commons` since the hpc tier); the array task runs `python -m lab_commons.hpc.worker` there.

## Platform parts: one verdict composed per platform

- ONE declaration, per marker, in the tested repo's pyproject, read AT `--sha` (`lab_commons.hpc.platforms`): `[tool.lab_commons.platforms]` `femm = ["windows"]`, `matlab = ["windows", "linux"]`. A marker not listed runs everywhere; platforms are `linux`, `windows`, `macos`. There is no `--not-covered` flag: the table is the one source.
- A part is named for the platform it RAN ON. The record `verdict gather` wrote becomes the `linux` part: `python -m lab_commons.dev.platformparts record-linux record.json --tier <gate|heavy>` writes it into the verdict ledger, STRICTLY -- PASS only if every covered id is `passed`/`skipped`/`xfailed`; any `failed`/`error` is FAIL; ANY `lost`/`missing` id makes the part INCONCLUSIVE and it is refused, never recorded (a FAIL claims the code failed; measured 2026-10-09, 50349 lost ids from a build that made no venv were recorded as a linux FAIL); a record covering nothing is refused. Its env names the cluster (`hpc:<cluster>:<platform>:python-<x>`), never the box that ingested it.
- **Every collected id is ASSIGNED to exactly one part, by one rule** (`lab_commons.hpc.platforms.assign`): the first of `linux`, `windows`, `macos` that can run it. A part's selection is a pure function of the commit's table and its collected ids, so every part can start at any time and in parallel; no part reads another part's record. The cluster's linux verdict uses the same rule for its `not-covered` set.
- Any other part calls `platformparts.select(root, sha, platform, collect=...)` (`collect` maps a marker expression to the ids it collects in that checkout), runs its assigned ids, and records what it `handed`: every other id with the platforms that can run it. A consumer exposes it as its gate runner's `--platform <name>`.
- Admission (`lab_commons.dev.admission`) accepts a whole verdict for HEAD OR the newest part per platform for HEAD when every id any part handed is assigned to a recorded part, in whichever order the parts were recorded. A FAIL part composes a FAIL (integration admits it and writes the gap; the trunk refuses). A missing part is refused naming the part and its command; an id no declared platform can run, or one a part handed though it is assigned to that very part, is refused by name. The trunk counts a composition only when every part is a PASS of a trunk tier.
