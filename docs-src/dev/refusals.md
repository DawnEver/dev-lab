# Refusals

When a deny hook refuses a command, it prints three lines: what was refused and why, the command to run instead,
and a `details:` pointer to a section of this page. Run the command it names. Each section below holds the full
reasoning for one universal row (`INJECTED-TEXT-IS-PROGRESSIVE`); a repo-local row is on that repo's own page.

A row marked HINT never refuses: the command runs and the same text reaches the agent as context. A row hints when
its hazard is speed or style rather than irreversible harm (toolchain plan P3, `dev_lab.dev.hooks.SEVERITIES`).

## The shape of a refusal

The budget is declared data in `dev_lab.dev.disclosure.BUDGETS`:

- `<ID>: <what was refused and why, as one clause>`
- the exact command to run instead (the door);
- `details: docs-src/dev/refusals.md#<id> (dev-lab)`, which points at the section below.

When a command targets another repo, the engine adds one header line naming that repo. `dev_lab.dev.famtests.injectedtext` runs the budget in a consumer's suite. `{remedy}` in an exit is the consuming repo's own door. `{python}` in an exit (and `<venv python>` in a door) is printed as the target checkout's own venv interpreter by ABSOLUTE path -- a linked worktree without one gets its main checkout's -- so the line runs from any cwd (2026-10-26: a relative `.venv` interpreter failed from another directory and the agent handed the command to the user). An exit is for the agent to run itself.

## BARE-TEST-INVOCATION

- **Why it is refused.** a hand-written test line has no VERDICT. An exit code cannot say whether the run COVERED what it selected, so a dead worker, a truncated run or a collection error that reported nothing all read as green -- and the reader has merged "the tests passed" with "nobody knows".
- **The exit.** Re-issue through the entry point that produces a verdict: {remedy}
- **Listing tests.** A collection (`pytest --collect-only` or `--co`) runs no test and claims no verdict, so that segment is admitted as written in every repo; a run chained beside it is still refused.

## FORGE-WRITE-VIA-CLI

- **Why it is refused.** a forge write through any client but the family door carries no PROVENANCE. The forge records only the token`s login, and every agent on a box shares one token, so an issue, comment, close or PR written this way cannot say which machine or which agent wrote it. The family door opens every body it writes with `[<machine> · <agent> · <branch>]`, read from HARNESS_MACHINE / HARNESS_AGENT.
- **The exit.** Write through the family door: {python} -m dev_lab.dev.forge issue create|comment|close|label, pr create|close (reads: issue list|view, pr view; token: auth login|status). A write the door has no verb for -- merge, edit, review -- is the integrator`s to make: report it rather than reaching for another client.

## GIT-COMMIT-AMEND

- **Why it is refused.** `--amend` does not act on YOUR last commit, it acts on HEAD -- and on a shared lane HEAD belongs to whoever committed most recently. This family has NO single-agent mode, so "I just committed" is not a safety argument; it is the exact condition under which this fires. MEASURED 2026-09-18 on `feat/consumer-c`: agent A committed, agent B committed 40 seconds later, and A amended to fix two digits in its OWN message -- rewriting B's commit and replacing B's message with A's. It was caught inside a minute through `git reflog` and the tree recovered byte-identical, so only the SHA moved; nothing about the recovery made that outcome likelier than losing the work.
- **The exit.** Do not rewrite -- land the correction FORWARD. Read what HEAD actually is first: git log -1 --format="%h %an %s". If the CONTENT is wrong, commit the fix on top. If only the message is wrong and nothing a reader acts on changes, record the correction where the work is reported and leave the commit alone; that is the right call once anything sits on top of it.

## NETWORK-VERB

HINT: a bare network verb loses only the retry; force, delete and no-verify pushes are refusals of their own.

- **Why it is said.** the forge is a REMOTE service that nobody in this family restarts, and a single transient auth/DNS/connection failure on any of these verbs reads as "blocked" -- which is the report the retry wrapper exists to prevent. Measured 2026-08-21 on a `git fetch`: it failed auth once and succeeded on the retry, and was reported blocked in between. Widened 2026-10-19 to every verb `dev_lab.dev.netverb.is_network_verb` names -- git's `-C`/`-c` spellings, `submodule update`, and uv's resolving verbs -- after a `uv sync` of a git dependency failed once on forge auth and a re-run passed.
- **The exit.** Re-issue through the retry wrapper, which retries 3x and then REPORTS with a diagnosis: {remedy}

## TREE-HAS-A-LIVE-RUN

- **Why it is refused.** a run executes its checkout's code and `.venv` for its whole life, so an edit, a merge, a checkout or an environment sync under it makes its result describe a tree that never existed. Measured 2026-10-19 in consumer-a: during a JMAG `deck run`, an agent edited a test, merged into the checkout and re-synced the venv the run executed from. The run is found WITHOUT its cooperation (`dev_lab.dev.liverun`, read off `lab_commons.census`): a process READS the tree when it is a Python interpreter working in it or an argument names a path in it, and the row binds only while one exists. `output/`, `.claude/` and `.venv/` are not the tree; a process executing from the venv locks the venv (`dep`), not the tree.
- **The exit.** Work in another worktree (git worktree add --detach .claude/worktrees/<name> <sha>), wait for the run, or stop it yourself: {python} -m dev_lab.dev.stoprun --pid <pid>.

## BACKGROUND-SHELL-IS-BOUNDED

- **Why it is refused.** a background shell has no lifetime of its own: `until ...; do sleep; done` waits, `forge watch --stream` and verify runs outlived their purpose for hours or days, and some outlived the session that started them (user demand 2026-11-15). The engine asks `dev_lab.dev.shelllife --admit` for the judgement. `dev_lab.dev.shellreaper`, wired at every stop (the one event that recurs inside a session), stops an agent shell past 50 minutes, or past the user's grant its line names, through stoprun's tree-kill, and never a tree holding a box seat, a `forge serve`, or a run the repo declares in `[tool.dev_lab.stoprun] spare`. Refused rather than rewritten: the hook API drops `updatedInput` for Bash.
- **The exit.** Start the line with its bound: `timeout 50m <command>`; a compound line goes whole: `timeout 50m bash -c '<line>'`. A longer life is the USER's (ruling 2026-11-15): the refusal of a longer bound names the `shell.lifetime` request (the SHA-256 of the command after its `timeout` prefix, and the minutes); write it under `output/logs/<yy>/<mm>/<dd>/consent/`, ask the user for the code, and once they approve run `python -m dev_lab.ops.consent grant <request.json> --code <the code they gave>`, then re-issue as `DEV_LAB_LIFETIME_GRANT=<credential id> timeout <minutes>m <command>`. The sweep honours that grant, verified at the shell's launch, and nothing else.

## HOOK-UNDER-FIVE-SECONDS

- **Why it is refused.** every hook source on one event shares a five-second ceiling (user ruling D24, 2026-11-17: a slow hook let a 30-second TOTP code expire), so each rendered row carries `timeout` 5 and the dispatcher keeps a far smaller share (`dev_lab.dev.agent_wiring.DISPATCH_BUDGET_S`). A row that can take longer is never cut or skipped: it is `detached`, run to completion by one background runner per repo (`dev_lab.dev.hookhandoff`), and its answer reaches the session at its next context event. A row past the budget at run time is handed to that runner the same way, and the dispatcher says so. A guard (`may_block`) cannot be detached: its answer is needed now, and the harness lets a call through when a hook times out, so a guard stays inline and fast.
- **The exit.** Make the row fast (no network, no long git or walk on the hook path, a cached read), or declare it `detached = true` in its `[[tool.dev_lab.agent_hooks]]` row; measure a dispatcher with `python -m dev_lab.dev.hookdispatch --timing <Event>`.

## TRACKED-CITES-NO-EPHEMERAL

- **Why it is refused.** A rem task journal (`.claude/tasks/<slug>/JOURNAL.md`) is append-only behind rem's task guard, so a line citing a git-ignored path, an untracked path under a stray root (`scratch/`) or a machine-local path can never be repaired once written -- and the commit-time scan (`dev_lab.dev.ephemeralrefs`) refuses it. Measured in dev-lab#419: four guards, each right, and no remedy any of them allowed. So the line is judged BEFORE `task.js log|decide|open-item|close-item|handoff` appends it, by the same predicate the commit-time scan runs. The row's pattern is only a prefilter in the engine; on a match the engine asks `dev_lab.dev.journaldoor --admit`, which reads the repo's ignore rules and tracked set -- so an ordinary shell call starts no Python. Only the appended words are judged: a chained `&& cat output/<file>` is not the journal's text, and a heredoc body a sink consumes is data.
- **The exit.** Rephrase the text before it is appended: cite a memory entry by name, or the path as a `<placeholder>` shape (`output/logs/<yy>/<mm>/<dd>/<kind>/`). A line already written is the user's to edit in an editor (the commit-time refusal says so).

## STRAY-FILE-REFUSED

- **Why it is refused.** A file somebody meant is staged; a program's artefact belongs in `output/`; a one-off script belongs in `scratch/`. An untracked, non-ignored file anywhere else is a file nobody claimed -- the 2026-10-20 vendor logs in the checkout root and the stray `uv.lock` (`dev_lab.dev.strays.stray_files`). It reports after each shell call and at Stop.
- **The exit.** One per file, by its kind: a file a known retirement declares gone is deleted through the door its row names and never staged -- the rows are the checkout's own data, `retired = [{ path = "...", what = "...", door = "..." }]` in its `[tool.dev_lab.placement]` (a repo using rem declares rem's retired generated memory index there, with rem's migration as the door), matched at any depth outside an archive, and a checkout that declares none gets no such exit; a file under a code root was meant -- `git add` it; a script is a one-off -- move it to `scratch/<yy>/<mm>/<dd>/<kind>/`; anything else is a program's data -- move it to `output/logs/<yy>/<mm>/<dd>/<kind>/` and make the program write there (a vendor tool writes into its cwd: give it a cwd under `output/`).

## WRITES-STAY-IN-THE-TREE

- **Why it is refused.** User requirement 2026-11-05: an agent session left scripts in the OS temp dir (Git Bash `/tmp` is the same directory). Outside a checkout nothing scans, ignores or cleans a file, so it outlives the session and nobody owns it. The write-prone roots are one declared set (`dev_lab.dev.writeroots.write_prone_roots`, extended by the machine file's `[writeroots]` `temp`/`census`/`excluded`): the OS temp dir, POSIX `/tmp` and `/var/tmp`, each fixed drive's and the home's `tmp`, `temp`, `var`, `src`, and a loose non-dot entry in the home. Refused: a Write/Edit/NotebookEdit there (the `codeplace` write hook), and a shell redirect, `tee`, `cp`/`mv`/`Copy-Item`/`Move-Item` target, `mkdir`, `touch`, `New-Item`, `Out-File`, `Set-Content` or `Add-Content` into one. Reading and deleting stay allowed. A write beneath a write-prone root is refused EVEN INSIDE A CHECKOUT there, in both halves: user ruling 2026-11-06 -- a checkout under such a root (the home `src` above all) is an abandoned old version, never a place to work. Never refused: the harness's own `<temp>/claude/` subtree, `lab-commons-notices`, and a cache named by `UV_CACHE_DIR`/`PIP_CACHE_DIR`/`RUFF_CACHE_DIR`. The Stop hook the stray census rides (`python -m dev_lab.dev.strays hook`) also names the scripts and notes a session left in a root; `python -m dev_lab.dev.tmpsweep [--apply] [--max-age-days N]` is the census and the sweep, which removes only temp-root entries older than the age in every file they hold, never a link, a checkout or a held file.
- **The exit.** A program's artefact goes to `output/logs/<yy>/<mm>/<dd>/<kind>/` and an experiment to `scratch/` of the checkout you work in.

## AGENT-RUNS-ITS-OWN-COMMANDS

- **Why it is refused.** A turn that ends by handing the user a command to run moves the agent's work onto the user, and the command usually fails from the user's cwd. The Stop hook reads the final message (`dev_lab.dev.handback`).
- **The exit.** Run the command through the shell tool with absolute paths and report the result. A guard's refusal names the door an agent uses; a permission-classifier refusal is a decision for the user, so ask for the decision, not for the command to be run. Only an interactive login, passphrase or GUI step may go to the user as `! <cmd>`, and only these (`handback.INTERACTIVE_ONLY`): `gh auth login`, `gh auth refresh`, `gcloud auth login`, `gcloud auth application-default login`, `az login`, `aws sso login`, `npm login`, `docker login`, `ssh-add`, `ssh-keygen`, `gpg --full-generate-key`, `claude login`, `codex login`, `/login`.

## IMAGES-BY-ABSOLUTE-PATH

- **Why it is refused.** User ruling 2026-11-22: an image delivered to the user is named by its ABSOLUTE path. A relative path resolves against a working directory the reader is not in -- the agent works in a worktree, the user reads from elsewhere -- so the figure cannot be opened from the message that announces it. The Stop hook reads the final message (`dev_lab.dev.imagepath`, called by `dev_lab.dev.handback`) and blocks the stop once.
- **The exit.** Say it again with every image named by its absolute path, resolved against the checkout it was written in. What is read is a path token ending in an image suffix (`imagepath.IMAGE_SUFFIXES`) after a file stem, in a markdown image, a code span or prose; an absolute path, a URL, a `data:` source, a pattern or template (`*.png`, `<name>.png`, `{stem}.png`) and a path through a shell variable pass. The text cannot tell a delivered image from a discussed one, so both are read.

## ARCHIVE-IS-NO-STORE

- **Why it is refused.** A bundle (like an `archive/*` tag or a copy under `output/`) parks unlanded work where nobody reads it again; origin's tags are versions only (`ONLY-VERSION-TAGS`, `dev_lab.dev.milestonebase`, user ruling 2026-11-23).
- **The exit.** Unlanded work is merged or discarded (`MERGE-OR-DELETE`): merge it through a PR, or land its discard with a declared `git merge -s ours` PR, then `branchprune delete <branch>` (a tag: `branchprune tag <tag>`).

## GIT-STASH

- **Why it is refused.** `refs/stash` is REPO-WIDE. It is one ref per repository, not per worktree, so a stash taken in one checkout is popped by whoever pops next -- in a family whose premise is a shared, possibly concurrent checkout, that is another agent losing work it never knew existed.
- **The exit.** Keep the work where its owner can see it. Either commit it on your own lane branch (a scratch commit is cheap and is named), or take a throwaway checkout: git worktree add --detach .claude/worktrees/<name> <sha>

## GIT-RESET

- **Why it is refused.** every form of `git reset` moves HEAD, the index or the working tree of a checkout, and in a shared checkout another agent may be committing there at that moment: `--hard` discards their edits, `--soft`/`--mixed` silently re-stage or un-stage what they meant to commit. SHARED-CHECKOUT said "never `git reset`" in prose and nothing refused it.
- **The exit.** Name the narrower act: unstage one path with `git restore --staged <path>`; undo a commit FORWARD with `git revert <sha>`; to start over, take a throwaway checkout: git worktree add --detach .claude/worktrees/<name> <sha>

## GIT-STAGE-EVERYTHING

- **Why it is refused.** `git commit -a`, `git add -A`/`--all`, `-u`/`--update`, `.` and a directory stage whatever is modified, including what another agent in the same checkout left unstaged -- an unstaged edit is not storage, and a wide stage turns it into somebody else's commit. The pattern reads only up to the first quote, so a message that mentions a flag is not one.
- **The exit.** Stage the paths you mean and check what is staged: `git add <path> <path>`, then `git diff --cached --stat`.

## PUSH-FORCE

- **Why it is refused.** every branch here is read by someone else, and rewriting a ref silently invalidates any verdict already taken against the old tree -- the verdict still cites a `tree=` address, and the tree it names no longer exists. `--force-with-lease` is refused with the rest: it protects against a ref that MOVED, not against a reader who already judged the ref as it was.
- **The exit.** Do not rewrite a shared ref: land the change FORWARD as a new commit on your own lane, then push without the force flag. If the history really must change, it changes on a branch nobody has judged yet.

## PUSH-REMOTE-DELETE

- **Why it is refused.** a main session may push without asking (MAIN-SESSION-PUBLISHES), and the allow row that opens the push is a glob -- it admits `--delete`, `-d`, `--prune`, `--mirror` and a `:<ref>` refspec exactly as readily as a plain push. Deleting a ref on origin is the one push nothing on the agent's side can undo: the local branch may already be gone, and another reader's verdict may cite the deleted tip. A raw delete checks nothing first; the 2026-10-21 ruling opened deletion only where it is PROVABLY lossless. This row reads the command's text and is the EARLY refusal; the guarantee is the pre-push row (`LOSSLESS-DELETE`, below), which judges every delete however it was spelled.
- **The exit.** LOSSLESS-DELETE: `{python} -m dev_lab.dev.branchprune delete <branch>...` fetches, deletes only when every commit on the branch is on integration or on another live origin branch / open PR head (naming that container) or, failing that, when every file the branch's own commits wrote is identical (mode and blob) on integration (a generated file, `famfiles.GENERATED`, never counts -- so a branch of sync merges deletes), and otherwise refuses naming the commits, the files carrying unlanded content and its two doors (MERGE-OR-DELETE, D22 -- no tags): MERGE what is still wanted through a PR, or LAND the branch by merging it into a `pr/` branch with `git merge -s ours`, declaring each conflicted file and each dropped test (`Merge-Audit:`), then re-run the delete. A remote TAG: `{python} -m dev_lab.dev.branchprune tag <tag>...` deletes one only when its (peeled) commit is an ancestor of origin's trunk or integration branch, records its name, ref sha and commit before a leased push, and keeps and names a tag pointing at uncontained work. Local cleanup stays a door: `python -m dev_lab.dev.branchset --apply` deletes merged LOCAL branches only and lists origin's.

## PUSH-NO-VERIFY

- **Why it is refused.** `--no-verify` skips the pre-push hooks -- admission and the trunk proof -- so the push publishes what no hook checked, while looking exactly like one that did not. No pre-push hook runs a test (VERDICTS-FROM-THE-FORGE), so the flag saves nothing.
- **The exit.** Push without the flag; the forge produces the part after the push. To check a change first, measure what you touched: {remedy}

## RAW-PROCESS-KILL

- **Why it is refused.** a raw kill stops what you NAMED, and a test worker names nothing on its own command line -- so the subtree that actually holds the box survives its parent. Measured twice in this family (2026-07-29, 2026-09-13): stopping a wrapper orphaned its children, and the orphan went on holding the CPU lock for a run whose own process was already dead.
- **The exit.** Kill the process TREE by its ROOT pid, children-first, and verify none remain: {remedy}

## WORKTREE-BASE-IS-EXPLICIT

- **Why it is refused.** `git worktree add <path>` with no commit-ish silently takes the CURRENT HEAD, which on a shared checkout is routinely not the tree you meant. MEASURED 2026-09-01: two agents were handed trees based on the wrong branch and each reasoned about a codebase nobody runs -- one of them for 130k tokens -- before noticing. A bare `HEAD` is accepted because it is a choice rather than an omission, but it is the weakest one available: HEAD moves, so two trees cut from it minutes apart can differ. Prefer the sha.
- **The exit.** Name the commit the tree starts from: git worktree add --detach .claude/worktrees/<name> <sha>

## WORKTREES-STAY-INSIDE

- **Why it is refused.** a checkout created OUTSIDE its repository is outside every scan, ignore rule and search that repository runs over itself, and outside the place the next agent looks for it. MEASURED 2026-10-03: eight worktrees across the family had been created as siblings of their repos, and the user ruled that day that it is forbidden family-wide.
- **The exit.** Put it inside the repository: git worktree add --detach .claude/worktrees/<name> <sha> (from the repo root; with -C, git -C <repo> worktree add --detach <repo>/.claude/worktrees/<name> <sha>). To relocate one: git worktree move <tree> <repo>/.claude/worktrees/<name>. A clone takes an explicit target <repo>/.claude/worktrees/<name> -- or is better a worktree. A FAMILY repo is the one clone that goes outside: into the siblings root, the directory holding the family's checkouts (`[repos]` in the machine file, `dev_lab.dev.family.members.siblings_root`), as `cd`s then ONE `git clone <url> <root>/<repo>` whose <repo> is new and named for the url, from a forge (scheme, host, owner) a sibling's `origin` already uses.

## WORKTREE-NAMES-ITS-TASK

- **Why it is refused.** User ruling 2026-11-22: a worktree's name must have a physical meaning related to its task, and an agent appending a string of hash is strictly forbidden. A tree named `agent-a1b2c3d4` or `fix-4ad12b6` tells the next reader nothing: not what it is for, not whose it is, not whether it may go. Hash-like (`dev_lab.dev.worktreename.HASH_LIKE_LEAF`) is `agent-<6+ hex>`, or a name that is, or ends after `-`/`_`/`.` in, six or more hex characters holding both a digit and a letter; a date, an issue number and a word spelled in hex letters pass. Only the directory a `git worktree add|move` makes is judged, never the commit-ish or the branch.
- **The exit.** Name it for what it does under its task, as its branch already is: git worktree add -b pr/<task>/<feature> .claude/worktrees/<feature> <sha>. A tree that already has such a name is renamed with git worktree move <tree> .claude/worktrees/<feature>; `dev_lab.dev.famtests.worktreeplace.assert_every_worktree_names_its_task` names each one, including a tree a harness made without a shell command, which the deny engine cannot see.

## BARE-INTERPRETER

- **Why it is refused.** `uv run` or `uvx` runs an interpreter somebody else chose -- uv's managed one -- not this checkout's venv, and `uv run` may also mutate the checkout's environment outside the checked dependency door. Each worktree owns `.venv`; main's environment belongs only to main, never to an unpopulated lane.
- **The exit.** Run this checkout's own venv interpreter, printed by absolute path: `{python} <args>`. If it is missing, `{python} -m dev_lab.dev.dep --bootstrap <worktree>` (the main checkout's interpreter, for a linked worktree) to create the target's own environment. Use the repo-declared dependency-sync door (`scripts/gate/dep_sync.py` where supplied) for dependency changes. Agents may run these specific checked doors; this does not permit arbitrary installers or silent main-environment mutation. A repo-declared CLI stays allowed.

## BARE-PYTHON

HINT: a bare interpreter mutates nothing; the hazard is a wrong interpreter, not harm.

- **Why it is said.** a bare `python`/`py` runs the interpreter the PATH chose, not this checkout's venv, so an import
  resolves against packages this checkout never declared and a result cannot be reproduced from the lock. It mutates
  no environment, which is why it hints (toolchain plan P3, 2026-10-23) while BARE-INTERPRETER, whose `uv run` may
  sync one, refuses.
- **The exit.** The same as BARE-INTERPRETER's: this checkout's own interpreter by absolute path,
  `{python} <args>`. If it is missing, `{python} -m dev_lab.dev.dep --bootstrap <worktree>` to create the target's own environment; main's environment belongs
  only to main.

## RECURSIVE-GREP

HINT: the hazard is minutes, not harm.

- **Why it is said.** `grep -r` walks the filesystem, so it descends into every git-ignored tree a checkout carries: `.venv`, `output/`, `target/`, nested worktrees. MEASURED 2026-10-05 in one consumer repo: `grep -r` over the repo did not finish in 4 min, `git grep -l` took 0.28 s, and about 66k git-ignored files were walked. A grep on a named file, a grep reading a pipe and `git grep` never walk, so they are permitted; the row keys on the recursion flag (`-r`, `-R`, a cluster such as `-rn`, `--recursive`).
- **The exit.** Search the tracked files: git grep -n <pattern> [-- <paths>] (add `--untracked` for new files), or the agent's built-in Grep tool, which honours `.gitignore` and the family `.rgignore`.

## RECURSIVE-DELETE

- **Why it is refused.** INCIDENT 2026-10-27: an agent hand-built a delete list from `git worktree list` and ran `Remove-Item -LiteralPath "\\?\<path>" -Recurse -Force` over it; one entry was a MAIN checkout, deleted with its `.git`, unpushed work and `output/`, past the recycle bin. The door that decides deletability existed and was bypassed. Refused in both shells: `rm -r`/`-rf`/`-fr`/`--recursive` (any order), `Remove-Item -Recurse` (any case or abbreviation, and its aliases `rm`/`ri`/`del`/`rmdir`/`rd`), `rmdir /s`, `rd /s`, `cmd /c rmdir /s`, `git worktree remove` (with or without `--force`), `git clean` with `-x`, `-X`, `-d` or `--directory` (a dry run is exempt only within its own argument list), and `shutil.rmtree` in interpreter code. A recursive delete that NAMES no target (`xargs rm -rf`, `... | Remove-Item -Recurse`) is refused: its targets arrive through a pipe and nothing proves them scratch. Permitted: a delete that names at least one target and whose EVERY target is a single token with no whitespace (even quoted) and no `..` anywhere, under system temp (`/tmp/`, `$TEMP`, `$TMPDIR`, `%TEMP%`, `$env:TEMP`, `AppData/Local/Temp`) or inside an `output/` tree; a non-recursive `rm file`; an `rmdir` of an empty directory; `git clean -n`.
- **The exit.** A checkout's `scratch/` (any checkout, a main one included): `{python} -m dev_lab.dev.scratch list` shows its untracked entries and sizes, `{python} -m dev_lab.dev.scratch clear [NAME ...] [--keep NAME ...] --yes` deletes the named untracked entries, or with no names those THIS session left (its start snapshots what predates it) -- never a tracked file, never outside scratch, refusing a link that escapes it, and clearing the Windows read-only/hidden attributes a nested `.git` carries. ## DOWNSTREAM-SYNCS-INTEGRATION

- **Why it is refused.** `forge sync` (`dev_lab.dev.forgesync`) updates a CHILD branch from its upstream set: integration first, then the refs its owner watches (the rule's statement is the registry row, `dev_lab.dev.rules`). A ref outside that set would bring another child's work in sideways; a detached HEAD, the trunk and the integration branch are not child branches (only the integrator moves integration, only `integrate promote` moves the trunk); a ref that names no commit cannot be trial-merged.

## SYNC-STARTS-FROM-A-COMMIT

- **Why it is refused.** a sync merges onto HEAD and commits the merge and its relock, so it starts from a commit: uncommitted tracked changes would ride into the merge commit, a half-done merge (`MERGE_HEAD` set, left by a killed commit, 2026-11-13) would be committed under the sync's message, and a path already staged would be swept into the relock commit (2026-11-07). Nothing is fetched, merged or relocked.
- **The exit.** Commit the changes (`git add <paths>; git commit`); conclude a half-done merge with `git commit --no-edit` or drop it with `git merge --abort`; commit or unstage (`git restore --staged -- <paths>`) what the index holds. Then rerun forge sync.

## SYNC-STOPS-ON-A-CONFLICT

- **Why it is refused.** every upstream ref is trial-merged in the object store first (`dev_lab.dev.trialmerge`); when any would conflict, NOTHING is merged, so the tree is never left half-merged by the command. The refusal names each conflicting ref and its files. Resolving a conflict is a judgement (`MERGE-RESOLUTION-DECLARED`), so it is the owner's.
- **The exit.** `git merge <the ref named>`, resolve those files, declare each in the merge commit, commit, run your tests, then rerun forge sync for the rest of the set.

## SYNC-STEP-FAILED

- **Why it is refused.** a step of the sync failed -- the fetch, a merge commit the commit hooks refused, or the relock (the dependency door, a renderer, the data pins, the relock commit). No step leaves a half-done state: an uncommitted merge is aborted and a failed relock restores every file it touched (user ruling 2026-11-07), so the next sync is not refused by a dirty tree. The cause line carries the step's own error.
- **The exit.** Fix what the cause line names (a merge commit that exited but left no pending merge names HEAD: `git log -1 <sha>`), then rerun forge sync.

## LOSSLESS-DELETE

- **Why it is refused.** a push deleted an origin branch whose content is held nowhere else, or one that is never deleted (the integration branch, the trunk, an open PR head). The pre-push row `lossless-delete` (`dev_lab.dev.pushdelete`) judges EVERY branch a push deletes on git's own ref lines, so a delete spelled any way -- a `$refs` variable assembled at run time, `xargs`, `eval`, a script -- meets the judgement `branchprune delete` makes (`dev_lab.dev.deletejudge.judge`): after `git fetch --prune origin`, the deleted sha must be on integration, on another live origin branch or an open PR head (a branch the same push deletes holds nothing), or every file its own commits wrote must be identical on integration, generated files aside. A tag holds nothing (user ruling D22: no archive tags). A branch the policy declares DERIVED -- a machine branch its producer regenerates whole, `[tool.dev_lab.integrator] derived = [{ branch = "pr/components-bump", producer = "dev_lab.dev.componentbump" }]` (decision D23) -- goes whatever it carries, and holds nothing for another branch. Measured 2026-11-17: nine branches holding unlanded commits went in one `git push origin $refs`, past the text-only `PUSH-REMOTE-DELETE` row.
- **The exit.** MERGE what is still wanted through a PR into integration, or LAND the branch by merging it into a `pr/` branch with `git merge -s ours` (declaring each conflicted file and each dropped test), then delete through `{python} -m dev_lab.dev.branchprune delete <branch>`, which judges afresh, names what holds the branch, and pushes its delete through this same hook. Close an open PR before deleting its head; the integration branch and the trunk are never deleted. A machine branch regenerated whole is declared `derived` with its producer, never exempted by name.

## LOSSLESS-DELETE-UNJUDGED

- **Why it is refused.** a push deletes a branch and the judgement could not be made: the repo's `[tool.dev_lab.integrator]` declares no `integration` (or a `derived` row naming no branch or no producer), the fetch of origin failed, or the forge's open PR heads could not be read. An unread answer is never a pass: the hook fails closed.
- **The exit.** Fix what the cause line names -- declare the integration branch, or wait for origin and the forge to answer -- and push again (`{python} -m dev_lab.dev.netverb -- git push ...` retries a transient failure).
## MACHINE-FILE-IS-RENDERED

- **Why it is refused.** The machine file (`lab_commons.config.config_path()`) is a RENDER of three layers -- the config source's family file, its host file, and the machine's own local tables (`dev_lab.dev.devhost`). A hand edit of a family or host key is lost at the next render; a hand edit of a local key changes a fact nobody recorded (user ruling 2026-11-15). The shell row refuses a redirection, `tee`, `sed -i`, or a `cp`/`mv`/`Set-Content` onto the file; the Write/Edit half is `dev_lab.dev.machineguard.refuse_write`. Reading it stays free. An edit the hooks cannot see (an editor) is named key by key, with its owning layer, by the next SessionStart drift notice (`devhost drift`).
- **The exit.** A family or host key: change `family.toml` or `hosts/<machine>.toml` in the config source through its pull request, then `python -m dev_lab.dev.devhost render --write`. A local key (`[repos]`, `[user]`): `python -m dev_lab.dev.devhost local set <table>.<key> <value>` (or `local unset <table>.<key>`); it backs the file up, re-renders and prints what changed.

## FAMILY-REPO-IS-CHECKED-OUT

- **Why it is refused.** The family's repos are declared once, in the config source's `[family_repos]` (remote and integration branch), and where each is checked out on this machine is `[repos]` (the local layer). A clone of a repo `[repos]` already maps is a second checkout that splits work between two trees (2026-11-15: an agent cloned a second copy of a family repo it did not find). The row matches `git clone` and asks `python -m dev_lab.dev.familyrepos clone-check` (`when: 'declared-repo'`); a url no family repo declares passes. Every session starts with one `repo <name> -> <path>` line per `[repos]` row (`MISSING` when absent), and `devhost drift` names a family repo with no path and a path for no family repo.
- **The exit.** Work in the registered checkout: `git -C <path> worktree add -b pr/<slug> .claude/worktrees/<slug> origin/<branch>`. If the registered path is wrong, `python -m dev_lab.dev.devhost local set repos.<name> <absolute path>`.

## Cross-repo refusals

When a refused command targets a repo other than the session's (its cwd, `cd X &&`, `git -C X`), the engine in `dev_lab.dev.agenthooks` adds one header line. If the target repo declares a door for the rule in its pyproject `[tool.dev_lab.doors]`, the header names that door and the target repo's exit replaces the session's. If it declares none and the rule's exit is a per-repo door (its row carries `needs`), the session's exit is never shown: a need whose family door reads no file of the target is sent to that door, printed with the session's interpreter (a network verb: `python -m dev_lab.dev.netverb -- git <verb>`; a raw kill: `python -m dev_lab.dev.stoprun --pid <pid>`); a bare test line names the target's own `<venv python> -m dev_lab.dev.verify -- <paths>` when that interpreter carries dev_lab, else the `[tool.dev_lab.doors]` row to declare. For any other rule the header says the target declares no door, and the refusal below it is the session repo's: any repo file it names belongs to the session repo and may not exist in the target.

## MSYS-PATH-REWRITE

- **Why it is refused.** Git Bash (MSYS) rewrites every POSIX-absolute argument into its own install root before any program sees it: `/opt/x/bin/python` arrives as `<git-install-root>/opt/x/bin/python`. A remote command carrying such a word cannot match the host's sudo rows or find its files (measured 2026-11-23: `sshhold run ops@<host> sudo -n /opt/... install` asked for a password). `dev_lab.dev.msyspath` names the rewritten words, Windows inside an MSYS shell only (`MSYSTEM` set), before `sshhold run` sends anything.
- **The exit.** Prefix the line with `MSYS_NO_PATHCONV=1`, or run the command as a planrun step: `python -m dev_lab.dev.planrun run --plan <plan.json> --digest <D> --steps <steps.json>` carries its argv as JSON data, which no shell rewrites.
